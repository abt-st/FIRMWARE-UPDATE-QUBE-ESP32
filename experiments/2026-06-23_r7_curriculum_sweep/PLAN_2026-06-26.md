## Paso 1 (mayor leverage, ~30 min) — ¿es la fricción siquiera la causa?

Comparar la telemetría del rig real contra la sim, corriendo **la misma política** en ambos.
Si en el real la política **manda la acción correcta pero el péndulo no responde** → es
fricción/torque (y el enfoque de fricción es válido). Si **manda acción distinta a la de sim
para el mismo estado**, o el real no llega al apex aunque la sim sí → el problema es latencia,
ruido de sensor o saturación del actuador, y **ningún sweep de fricción lo arregla**.

Script: **`diagnose_real_vs_sim.py`**

```powershell
# Rig encendido, AP del ESP32 conectado (default IP 192.168.4.1). Pendulo colgando.
uv run python experiments/2026-06-23_r7_curriculum_sweep/diagnose_real_vs_sim.py `
    --ip 192.168.4.1 `
    --model experiments/2026-06-23_r7_curriculum_sweep/models/r7_cur0.3_s0_best.zip `
    --episodes 3 --scale 0.85
```

Genera `diagnose_real_vs_sim_<ts>.csv` (trazas crudas real+sim por step) y un resumen en
consola: ¿llega al apex el real?, hold real vs sim, fracción de acción saturada en el apex,
|alpha_dot| en el apex. Opcional `--friction-mult 100` agrega una tercera traza sim a esa
fricción para ver si reproduce el comportamiento real.

**Lectura del resultado → rama:**
- Real llega al apex pero **no aguanta**, acción saturada / |alpha_dot| decae rápido al subir →
  **fricción/torque confirmado** → Paso 2 (medir el multiplicador) → fine-tune dirigido.
- Real **no sube como la sim** o acción real ≠ acción sim a igual estado → **no es fricción** →
  investigar latencia HTTP (50 Hz real?), filtro de velocidad, escala de torque, deadzone.
  No tiene sentido otro sweep de fricción.

## Paso 2 (~1 tarde) — fijar el multiplicador de fricción con un número

Solo si el Paso 1 confirma fricción. Spin-down libre del péndulo: llevarlo a ~45° desde el
reposo (colgando), soltar sin torque, registrar `alpha(t)`. El decaimiento de la envolvente da
el amortiguamiento real, y lo **matcheamos contra la sim** barriendo el Dp para obtener
directamente el `fricción×N` que parametriza el sweep (en vez de adivinar 20–130×).

Script: **`measure_friction_spindown.py`** (dos subcomandos)

```powershell
# (a) CAPTURA: motor en 0 PWM (modo 6, a=0), suelta el pendulo cuando diga "GO".
uv run python experiments/2026-06-23_r7_curriculum_sweep/measure_friction_spindown.py capture `
    --ip 192.168.4.1 --duration 12 --out spindown_real.csv

# (b) ANALISIS: ajusta el decaimiento real y barre Dp en sim para encontrar el match.
uv run python experiments/2026-06-23_r7_curriculum_sweep/measure_friction_spindown.py analyze `
    --csv spindown_real.csv --dp-mults 1 10 20 40 70 100 130
```

Salida: `fricción×N` medido (con t_half real vs sim). Repetir la captura 3+ veces y promediar
(el sistema-ID previo fue n=1 e "inflado por acoplamiento del brazo").

la semilla pesó más que la fricción) a esa fricción, **evaluando a 100 ep desde el principio**.

```powershell
